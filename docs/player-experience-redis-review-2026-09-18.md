# Player experience and Redis review — 2026-09-18

Read-only code investigation of checkout `77640b0`, prompted by growth from 250–300 to 5,000+ DAU and 100,000+ race starts per day. This document is the only change made by the investigation. Production logs, deployed revision, peak request rates, and hosted Redis timings were not available; code paths below establish possible failures, not the frequency or cause of each observed production incident.

## Findings tied to player symptoms

1. **Last two Campaign tracks cannot create challenges: confirmed validator defect.** `src/server/head-to-head-model.ts:61–62` accepts only `numbered-v1-00` through `13`; the manifest also contains `14` (Square Root) and `15` (Half Life). Origin resolution returns null, causing `head-to-head-service.ts:637–639` to return “No verified result is available for this challenge.” Direct execution of the exported predicate and origin resolver accepted 13 and rejected 14/15. Use manifest membership as the authority and cover all stages; Redis tuning does not address this.
2. **Brag can succeed and still report failure.** `src/server/head-to-head-share.ts:204` posts the Reddit comment before token deletion at 234 and awaited lock release at 248. Either Redis operation can throw after a valid comment exists. Contain cleanup errors and reconcile a consumed preview to its posted comment. A receipt alone cannot make Redis and Reddit atomic: recovery must handle a crash or receipt-write failure after posting, without blindly posting again.
3. **Daily can save a result and still return “submit failed.”** After accepted competition persistence, `src/server/daily-gp-store.ts:3607–3618` awaits standings, car unlock reads, the completed-race event, lock cleanup, and profile update through `Promise.all`. An auxiliary rejection reaches the generic 500 in `routes/competition-routes.ts:121`. Acknowledge the durable verified result independently of optional response enrichment. Preserve missing reward/profile work through an explicit retry/reconciliation mechanism; do not silently discard it.
4. **Head to Head conflates temporary confirmation failure with unverified results.** `game/head-to-head/engine-methods.js:510–565` makes a single confirmation attempt and turns transport/server failures into the error finish state. The server also awaits reward writes and a car-unlock snapshot after successful validation/persistence (`head-to-head-service.ts:1115–1135`). Separate temporary confirmation failure from a rejected replay, retain an owner-bound replay, and retry transient failures with bounded jitter/backoff. Never display a verified win before authoritative confirmation. Daily/Campaign already have a verification queue; do not assume every “Unverified” report has the same cause.
5. **Startup has an eight-second client timeout and avoidable work.** `game/storage.js:44` defines the bootstrap deadline. Player bootstrap performs profile upsert and, for returning players with data, completed-race backfill before reading unlock state (`daily-gp-store.ts:3278–3312`). A timeout or thrown dependency can trigger the synchronization prompt. Reuse request-local reads and skip already-persisted reward events; separate nonessential bookkeeping from authoritative identity/preferences/unlocks. Keep transfer gates and confirmed-owner fallback intact. Hosted timing is needed to attribute the user's failures.

## Optimization order

### First: make success acknowledgements reliable

Fix items 1–4 before broad storage redesign. Avoid rerunning successful verification and mutations solely because rank, garage enrichment, cleanup, or a response was lost. Introduce stable, owner-bound submission identifiers/receipts where necessary, with replay/contract matching, and handle retryable contention separately from invalid replay. Preserve guest-transfer fencing and required persistence guarantees.

### Next: remove repeated work from frequent requests

- **Completed-race reward:** `car-unlock-store.ts:333` enters the promotion-safe event writer for every call even though the field is permanent. Use evidence of the persisted `race:completed` field to skip redundant writes, reusing an existing snapshot where possible. Cosmetic unlock evidence is insufficient. Keep the safe writer for missing fields.
- **Campaign bootstrap:** `campaign-store.ts:510–580` probes all 16 stage entries/scores for repair; standings then performs rank/count reads for all stages. Reuse entries from progress recovery, batch compatible reads, and defer display-only standings until needed. Progress and unlock correctness must remain authoritative. Do not simply remove recovery or launch all repair transactions concurrently.
- **Campaign-origin Head to Head:** `head-to-head-runtime.ts:311–313` repairs every stage although the request concerns one. Scope that repair to the origin stage: the normal repair probe count falls from 32 to 2, excluding authentication, progress recovery, other reads, and writes.
- **Expired-guest cleanup:** `campaign-store.ts:346–397` performs up to 16 × 4 queued stage commands, plus progress deletions and expiry-ledger removal, inside a transaction; multiple player-facing endpoints await the best-effort wrapper. Move maintenance to bounded scheduled work and preserve refreshed-expiry rechecks and ownership protections. Schedule durable work explicitly rather than relying on unawaited request tasks.
- **Analytics:** `analytics-store.ts:343–353` refreshes eight TTLs per recorded event. At 100,000 recorded starts this alone is 800,000 expiry calls, excluding finishes; actual coverage must be measured. Reduce refresh frequency with recoverable expiry maintenance while preserving day/month and rolling-ledger retention. Keep presence/cohort counting semantics; do not expire rolling ledgers only at creation.
- **Daily PB summaries:** `daily-gp-store.ts:3034` reads/seeds up to seven challenges sequentially. Separate pure reads from write/backfill work and use bounded batching/concurrency.

Existing optimizations must not be counted again: leaderboard entry/profile reads already run concurrently, PB records already use batched multi-field reads, and Head to Head challenge storage already combines SET with expiration.

## Capacity and validation

100,000 starts/day averages about 1.16 starts/second. That does not measure peak concurrency, commands per request, finishes, retries, or maintenance. Optimize measured request fan-out and transaction duration before assuming Redis throughput or storage capacity is exhausted.

Current official documentation is internally inconsistent: its transactions prose says 30 concurrent blocks, while its platform table says 20; both give a five-second timeout. Confirm the effective installation limit with Reddit. The table lists 40,000 commands/second and says pipelining is unsupported. Source: https://developers.reddit.com/docs/capabilities/server/redis (accessed 2026-09-18). Historical hosted transaction-limit errors are recorded in `redis-integrity-validation-2026-08-12.md`; they do not prove the cause of today's incidents.

Instrument endpoint p50/p95/p99, Redis calls and transaction duration per request, conflicts/concurrency failures, replay rejection reasons, and whether a failure occurred before or after persistence/posting. Correlate with request IDs without logging tokens or full replays. Track verified acknowledgement rate and duplicate comments as player-facing outcomes.

Before deploying fixes, inject failures after comment creation and score commit; verify retries avoid duplicates and preserve ownership/rewards. Cover all manifest stage IDs, transient Head to Head recovery, transfer contention, and returning-player bootstrap. Run focused regressions, the full suite, build, and a bounded hosted burst comparison separately. This investigation ran the stage predicate/origin reproduction only; it did not run the full suite or hosted load testing.
